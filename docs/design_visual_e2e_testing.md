## 一句话看懂：什么是“纯视觉 AI 盲测”？

简单来说，就是**请一个完全没见过这个软件的“AI 小白用户”坐在电脑屏幕前**：
* 我们**不告诉它后台代码**，也不给它任何内部暗号；
* 只给它看电脑屏幕截图，并给它一个简单目标：“**请按照屏幕上的提示，把聊天记录导出来**”；
* 它像真人一样用眼睛认路、用鼠标点击。如果它中途卡住了、点不到按钮、或者被提示框挡住了，就说明我们的**产品界面有 Bug，或者设计得太反人性了！**

## 为什么现在的测试还不够？（三个生活中的真实痛点）

我们项目目前其实已经有一套很严密的自动化测试了（比如自动化打字、自动化导出、数据校验等），但它们全都是**“程序员视角”的传统代码测试**。

这种测试有一个致命弱点：**它不长眼睛，只看后台代码**。

这就好比去餐厅检查卫生，传统测试只是打电话问厨房电脑：“冰箱运转正常吗？”电脑说正常就打满分。但真实情况可能是——厨房天花板正在漏水，客人根本没法吃饭。

### 痛点 1：气泡“自杀式遮挡”（最经典的真实事故）
新用户安装插件后，界面会弹出一个新手向导，气泡上写着“请点击这里开始同步”，并画了一个箭头指向“同步按钮”。  
* **传统测试的盲区**：测试脚本直接向底层的“同步按钮”发信号，按钮响应了，测试顺利通过！
* **真人的绝望现场**：气泡自己的大肚皮刚好把那个按钮给**死死盖住了**！真实用户只能看见提示气泡，却根本点不到被盖住的按钮，直接被困在第一步。

### 痛点 2：文字被截断、变形或重叠
在某些小屏幕、或者开启了英文模式时，按钮里的文字太长了，比如“导出为 ZIP 压缩包”被挤成了“导...”，或者两行字叠在了一起成了黑色墨团。  
* **传统测试的盲区**：测试脚本去后台搜查：“页面里有没有这几个字？”后台回答：“有！”测试直接判定通过。
* **真人的绝望现场**：人肉眼看过去，界面已经支离破碎，根本不知道这块黑乎乎的是什么。

### 痛点 3：弹窗蒙层“形同虚设”
有时候弹出了一个确认对话框，后面本来应该有一层半透明的灰色遮罩，防止用户误触背后的东西。  
* **传统测试的盲区**：脚本依然能直接触发背景里的各种按钮。
* **真人的绝望现场**：用户以为点了背景可以取消，结果直接误删了数据。

> 💡 **小结**：传统测试能证明**功能逻辑能跑通**，但只有视觉测试能证明**人类肉眼看起来是舒适的、手指是能点到的**。

## 这个 AI 测试员是怎么工作的？（看 ➔ 想 ➔ 动 三步闭环）

整个测试过程就像人类在电脑前操作一样，分为三个连续循环的动作：

```text
┌─────────────────┐       ① 眨眼截图 (纯图片)       ┌─────────────────┐
│                 │ ──────────────────────────────> │                 │
│   Chrome 浏览器  │                                 │   AI 视觉大脑   │
│  (正在运行的网页) │ <────────────────────────────── │  (多模态大模型)  │
│                 │       ③ 真实模拟鼠标光标点击     │                 │
└─────────────────┘                                 └────────┬────────┘
                                                             │
                                                             ▼
                                                    ② 动脑筋思考：
                                                    "我看到中间有个蓝色按钮
                                                     上面写着'下一步'
                                                     它没有被任何东西遮挡
                                                     我应该去点它！"
```

### 1. 看（纯视觉，绝不看后台代码）
测试程序直接对浏览器窗口进行高保真截屏，生成一张普通的 PNG 图片送给 AI。AI **看不到任何 HTML 代码、看不到任何标签 ID**，它面对的视野跟普通人一模一样。

### 2. 想（凭借人类常识进行决策）
AI（比如 Gemini 2.0 视觉模型）看着这张图片，开始思考：
* “左边是一个向导卡片，提示我进行第 2 步；”
* “右边有一个闪烁的高亮区域，里面写着‘增量同步’；”
* “根据常识，我现在应该去点这个‘增量同步’按钮，它的位置大约在屏幕横向 70%、纵向 20% 的区域。”

### 3. 动（真正的物理鼠标，严格执行碰撞测试）
AI 把想点击的屏幕坐标告诉测试程序。测试程序**不会调用任何代码接口**，而是模拟真实的鼠标硬件：
1. 把光标平移到目标坐标上（触发网页上的鼠标悬浮效果）；
2. 真实按下鼠标左键；
3. 真实抬起鼠标左键。

> **为什么说这是最真实的检验？**  
> 浏览器内核自身有一套“物理碰撞检测”逻辑。如果这时候恰好有一个弹窗浮层挡在按钮正前方，**这次鼠标点击就会结结实实地打在浮层上，按钮根本不会被触发！** 这就逼得我们在写前端样式时，必须确保层级和排版绝对合理。

## 它能帮我们抓住哪些传统测试发现不了的 Bug？

| 检查维度 | 传统代码自动化测试的表现 | 纯视觉 AI 盲测的表现 |
| :--- | :--- | :--- |
| **按钮被弹窗挡住** | 假装没看见遮挡，直接穿透点击（通过 ❌） | 鼠标被遮挡物挡下，按钮点不中，直接报错（发现 Bug ✅） |
| **文案被挤爆截断** | 只要后台代码里有这段文本就判定及格（通过 ❌） | AI 发现文字变成了省略号或乱码，报告排版缺陷（发现 Bug ✅） |
| **操作入口不明显** | 脚本带着死记硬背的坐标直奔目标（通过 ❌） | AI 找了半天找不到去哪点导出，报告交互引导不清晰（发现体验 Bug ✅） |
| **深色模式黑底黑字** | 代码测试根本不渲染颜色（通过 ❌） | AI 发现文字和背景融为一体看不清，立即告警（发现对比度 Bug ✅） |

## 零基础常见疑问解答 (Q&A)

### Q1：这个测试跑起来的时候，我的电脑鼠标会被它抢走乱飞吗？
**答：完全不会！**  
它是通过 Chrome 浏览器底层的内部调试通道（CDP）把点击信号送进浏览器渲染窗口里的。你的操作系统鼠标仍然归你自由支配，你完全可以一边让它在后台跑测试，一边自己写文档或刷网页。

### Q2：为什么一定要让这个 AI“完全没有背景知识”？
**答：为了最真实的模拟小白用户。**  
如果我们事先在代码里告诉它：“按钮的 ID 叫做 `#btnSync`，你要去点它”，那它就变成了“背过答案的考生”，只能测出代码跑不跑得通，却测不出这个按钮在普通人眼里到底能不能找到。只有让它“一无所知”，才能倒逼我们的产品把每一个按钮的文案、图标、箭头指引都做到一目了然。

### Q3：跑这种测试会不会很贵、很慢？
**答：极快、极便宜。**  
现在的多模态模型（比如 Gemini 2.0 Flash）看一张图只需要不到 1 秒钟。走完一整套 5~8 步的向导与导出流程，大约只需要 **20 秒左右**。由于每次只发几张小截图，调用一次的总成本还**不到人民币 1 分钱**。

## 两阶段落地计划

为了不影响现有的快节奏开发，我们分两步将其融入发布流程：

### 阶段一：视觉“质检员”（轻量快捷，零改动接入）
* **做法**：在我们现在的自动化测试脚本每跑一步时，自动咔嚓拍一张高清截图存下来；
* **效果**：测试跑完后，把这一组截图打包扔给 AI，让它当一个挑剔的“UI 质检员”，审查：“这几张图里有没有文字重合？气泡有没有挡住按钮？排版有没有塌陷？”如果发现了，自动生成一份视觉体检报告。

### 阶段二：完全自主的“AI 小白测试员”（独立专项盲测）
* **做法**：提供专门的运行指令（如 `npm run test:visual`）；
* **效果**：在新版本正式发布到 Chrome 应用商店前，让 AI 盲测员独立通跑一遍所有向导与导出功能，只有当一个零背景知识的 AI 都能顺利搞定所有操作时，才允许版本发布上线。

## 技术附录：它是如何做到不作弊的？（选读）

对于想要了解一点底层技术细节的同学，这里是它能够做到“纯视觉且不作弊”的核心机制：

1. **截屏通道**：调用 Chrome 的 `Page.captureScreenshot`，直接获取当前视口渲染出来的原始图片数据，不依赖任何屏幕录制外挂软件；
2. **位置定位**：AI 识别到按钮后，返回该按钮在图片中的归一化范围比例（例如：`[上方 20%, 左侧 40%, 下方 25%, 右侧 50%]`），程序取这个矩形的中心点作为点击坐标；
3. **物理派发**：程序向 Chrome 的 `Input.dispatchMouseEvent` 发送三个连续事件：`mouseMoved`（移入）➔ `mousePressed`（按下）➔ `mouseReleased`（抬起）。这三个事件会直接被交由 Chrome 的排版渲染流水线（Hit-Testing）处理，实现 100% 贴近人类真实手指点击的物理效果。
